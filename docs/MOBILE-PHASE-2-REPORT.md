## ۱. گام اول — seed مدیر: پارامتری شد + هشدار «سایه‌ی نقش»

`scripts/dev-seed-mobile-manager.sql` از این پس شماره را می‌پذیرد:

```
psql -d nir_dev -v ON_ERROR_STOP=1 -f dev-seed-mobile-manager.sql                      # پیش‌فرض 09120000003
psql -d nir_dev -v ON_ERROR_STOP=1 -v phone=09XXXXXXXXX -f dev-seed-mobile-manager.sql  # شماره‌ی دلخواه
.\psremoting\dev-seed-mobile-manager.ps1 -Phone 09XXXXXXXXX                             # اجرای از این ماشین
```

* id است به‌صورت `usr-mobile-test-manager-<phone>` ساخته می‌شود تا هر شماره رکورد مستقل داشته باشد؛
  username همان شماره است (هم‌راستا با قرارداد موجود)، `password_hash` خالی (حساب فقط OTP).
* پرچم `\if :{?phone}` یعنی اجرای بدون آرگومان **رفتار قبلی را مو به مو حفظ می‌کند** (idempotent).
* **افزوده‌ی مهم:** یک بررسی «سایه‌ی نقش» اضافه شد. ترتیب تشخیص نقش در `mobileAuth.ts` این است:
  `drivers.phone → DRIVER`، `farmers.phone → FARMER`، `users.phone → نقش کاربر`. پس اگر شماره‌ی شما
  از قبل روی یک راننده/مرغدار باشد، حتی پس از seed هم ورود با آن شماره به نقش **راننده/مرغدار** می‌افتد
  و صفحات مدیر باز نمی‌شود. اسکریپت این حالت را با خط `SHADOW|driver|...` یا `SHADOW|farmer|...` **گزارش**
  می‌کند (بی‌صدا «درست»ش نمی‌کند، چون تصمیم با شماست: شماره‌ی دیگر یا حساب آزمایشی عمدی).

### آنچه منتظر شماست
در پیام شما شماره به‌صورت جای‌نگهدار `[شماره خود را اینجا بنویسید]` مانده بود، بنابراین seed برای شماره‌ی
شخصی شما اجرا **نشده** است. با دریافت شماره، یک دستور کافی است:

```powershell
.\psremoting\dev-seed-mobile-manager.ps1 -Phone 0912XXXXXXX
```

خروجی باید یک خط `MANAGER_SEED|0912XXXXXXX|role=MANAGER|phone=0912XXXXXXX` بدهد و (در حالت مطلوب) هیچ خط `SHADOW` نداشته باشد.

**خروجی واقعی دو اجرای امروز (اثبات مسیر پارامتری و هشدار سایه):**

```
# با آرگومان: شماره‌ی راننده‌ی تستی فاز ۱
PHONE: 09120000001
MANAGER_SEED|09120000001|role=DRIVER|phone=09120000001   <- رکورد موجود دست‌نخورده ماند (نقش DRIVER)
SHADOW|driver|<نام راننده>                                <- هشدار: این شماره در نقش راننده باقی می‌ماند

# بدون آرگومان (پیش‌فرض، idempotent)
PHONE: 09120000003
MANAGER_SEED|09120000003|role=MANAGER|phone=09120000003
```

**نتیجه‌ی عملی:** seed به زور شماره‌ی یک راننده/مرغدار را به مدیر تبدیل **نمی‌کند** (چون INSERT به‌خاطر
تکراری بودن شماره رد می‌شود و نقش موجود دست‌نخورده می‌ماند). پس اگر شماره‌ی شما از قبل در سیستم ثبت شده
باشد، یا شماره‌ی دیگری بدهید، یا صریحاً تصمیم بگیریم نقش آن کاربر عوض شود — تصمیمی که با شماست و اسکریپت
بی‌صدا انجامش نمی‌دهد.

## ۲. گام دوم — مهاجرت `0006_mobile_trip_status.sql`

تا پیش از این، «وضعیت بار» فقط دو حالت **مشتق‌شده** داشت: `delivered` / `in_transit` — هر دو بر اساس
وجود ردیف در `delivery_proofs`. یعنی جریان واقعی راننده در جاده (تخصیص → رسیدن به مبدأ → بارگیری →
رسیدن به مقصد → تخلیه → تحویل) هیچ‌جا ذخیره نمی‌شد و دفتر کارخانه نمی‌توانست ببیند کامیون کجاست.

```sql
ALTER TABLE invoices ADD COLUMN IF NOT EXISTS trip_status TEXT;
ALTER TABLE invoices ADD COLUMN IF NOT EXISTS trip_status_at TIMESTAMP;
CREATE INDEX IF NOT EXISTS idx_invoices_trip_status ON invoices(trip_status);
```

* افزودنی + idempotent؛ **`NULL` یعنی «گزارش نشده»** و در آن حالت API همان رفتار قبلی را از رسید
  تحویل استنتاج می‌کند (`assigned` یا `delivered`) — پس معنی هیچ ردیف موجودی عوض نمی‌شود.
* وب و worker باسکول این ستون‌ها را نه می‌خوانند و نه می‌نویسند (شعاع انفجار صفر برای نرم‌افزار اصلی).
* آینه‌ها به‌روز شدند: `server/db/migrate.ts`، `server/db/schema.ts` (Drizzle + ایندکس) و
  `runtimeDdl` در `tests/farmerMerge.test.ts` (آینه‌ی PGlite).
* اجرا روی **dev** با اسکریپت جدید `psremoting/dev-mobile-phase2-db.ps1` (گارد: اگر `DATABASE_URL` به
  `nir_dev` اشاره نکند، اجرا متوقف می‌شود) و روی دیتابیس **محلی** `nir` (برای تست‌ها):

```
DEV:  trip_status | text      ·  trip_status_at | timestamp without time zone  ·  idx_invoices_trip_status
      reported=0 null=3123     ← همه‌ی ۳٬۱۲۳ حواله دست‌نخورده و «گزارش‌نشده»
LOCAL: trip_status | trip_status_at
```

## ۳. گام سوم — اندپوینت‌های جدید/اصلاح‌شده

### ۳-۱. `GET /api/mobile/driver/loads` — صفحه‌بندی واقعی تاریخچه (G-16)
پیش‌تر کل لیست با `.limit(100)` سقف خورده بود؛ پرکارترین راننده‌ی dev **۵۲۶ بار** دارد، یعنی ۴۲۶ سفر
برای اپ **وجود نداشت**. اکنون:

| پارامتر | پیش‌فرض | توضیح |
|---|---|---|
| `page` | `1` | شماره صفحه |
| `limit` | `100` | اندازه صفحه (سقف سخت ۲۰۰ — درخواست `limit=9999` به ۲۰۰ کلمپ می‌شود) |
| `scope` | `all` | `active` = بدون رسید تحویل، `completed` = دارای رسید |

* فیلترِ «رسید دارد/ندارد» **در SQL** اجرا می‌شود (`NOT EXISTS / EXISTS` روی `delivery_proofs`)، پس
  صفحه‌ی «تحویل‌شده‌ها» واقعاً صفحه‌ای از تحویل‌شده‌هاست، نه برش تصادفی از همه‌ی بارها.
* فیلدهای جدید پاسخ: `scope, page, limit, total, totalPages, hasMore, activeCount, completedCount`
  و در هر آیتم `tripStatus` و `tripStatusAt`.
* **سازگاری عقب‌رو:** با پیش‌فرض‌ها پاسخ برای APKهای قبل از فاز ۲ عیناً همان قبلی است (صفحه ۱، ۱۰۰ ردیف،
  هر دو لیست) — فیلدهای اضافه نادیده گرفته می‌شوند.

### ۳-۲. `PATCH /api/mobile/driver/loads/:invoiceId/trip-status` (G-8)
بدنه: `{ "status": "assigned|at_origin|loading|at_destination|unloading|delivered|cancelled" }`

قواعد (همه سمت سرور اعمال می‌شوند، پس هیچ صفحه‌ای نمی‌تواند سفر را خراب کند):

1. **فقط رو به جلو**: از `loading` نمی‌توان به `at_origin` برگشت → `409` (صف آفلاینِ قدیمی سفر را عقب نمی‌برد).
2. **`delivered` فقط با رسید تحویل**: بدون ردیف `delivery_proofs` → `409`. دکمه جای سند را نمی‌گیرد.
3. **`cancelled` پایانی است**: از هر وضعیتی جز `delivered` قابل ثبت است و بعد از آن بازگشت → `409`.
4. **تکرار همان وضعیت → `200` با `unchanged: true`** (retry آفلاین خطا نیست).
5. **مالکیت**: راننده فقط بار خودش را تغییر می‌دهد (FK، و در نبود FK همان تطبیق نام/تلفنِ مسیر
   `/driver/loads`)، مدیر/ادمین می‌تواند هر باری را اصلاح کند → در غیر این صورت `403`.
6. وضعیت نامعتبر → `400`، حواله‌ی ناموجود → `404`.

**هم‌راستایی دوطرفه:** ثبت رسید تحویل (`POST /driver/delivery-receipt`) هم اکنون `trip_status='delivered'`
و `trip_status_at` را روی حواله می‌نویسد (با گارد `IS DISTINCT FROM` تا retry چیزی را بازنویسی نکند)، پس
دو منبع هرگز با هم تناقض پیدا نمی‌کنند.

### ۳-۳. `GET /api/mobile/manager/unmatched-drivers` (G-7)
حواله‌هایی که **نام راننده دارند ولی `driver_id` ندارند**، گروه‌بندی‌شده بر اساس همان نام:

* گروه‌بندی با `textMatchKey` (همان نرمال‌سازی ی/ي، ک/ك، ZWNJ و ارقام) و نمایش با `normalizePersianText`؛
* برای هر گروه: `count`، تفکیک `exitCount`/`entryCount`، `oldestDate`/`newestDate`، شماره‌های نمونه،
  `phones` و `invoiceIds` (حداکثر ۲۰۰ شناسه برای جلوگیری از پاسخ‌های حجیم)؛
* **پیشنهاد راننده** با اولویت شفاف: `phone` (شماره‌ی روی حواله متعلق به یک راننده) → `name-exact`
  (نام نرمال‌شده دقیقاً یک راننده) → `name-close` (فاصله ویرایشی ≤ ۲، صرفاً پیشنهاد) و در صورت
  تعلق نام/شماره به بیش از یک راننده: `ambiguous` (هیچ پیشنهادی داده نمی‌شود).
* فیلترها: `type=entry|exit`، `search=`، `page`/`limit` (پیش‌فرض ۵۰)؛ سقف اسکن ۵٬۰۰۰ ردیف با پرچم
  `truncated`؛ دسترسی فقط `ADMIN|MANAGER`.
* **عمداً فقط-خواندنی است:** این اندپوینت هیچ نوشتنی انجام نمی‌دهد. عملِ نوشتن (ساخت/اتصال راننده) در
  افزایش بعدی با تأیید صریح مدیر می‌آید تا یک تطبیق تقریبی نتواند بی‌صدا حواله را به راننده‌ی اشتباه بچسباند.

## ۶. نقشه‌ی افزایش‌های بعدی فاز ۲ (به ترتیب ارزش برای کار شما)

1. **صفحه‌ی کامل حواله‌های ورود/خروج در اپ (فوریت بالا).** `RemittancesScreen` امروز بدون هیچ پارامتری
   `/api/invoices` را می‌خواند و ۵۰ ردیف آخر را **سمت کلاینت** فیلتر می‌کند؛ سرور از قبل
   `type/search/startDate/endDate/page/limit` را پشتیبانی می‌کند. کارِ کلاینت: تب‌های خروج/ورود روی سرور،
   فیلتر بازه‌ی تاریخ (تاریخ‌شمار از قبل در اپ هست)، دکمه‌ی «بیشتر»/صفحه‌بندی و نمایش `total`
   (اکنون: خروج ۲٬۳۹۳ و ورود ۷۱۳ حواله).
2. **صفحه‌ی «راننده‌های نامطابق» در اپ** — اتصال به اندپوینتِ آماده‌ی G-7 + نمایش گروه‌ها/پیشنهادها و
   در افزایش بعد: دکمه‌ی «اتصال به راننده» / «ساخت راننده» با تأیید صریح.
3. **UI وضعیت سفر در «بار‌های من»** — دکمه‌ی گزارش وضعیت + تایم‌لاین سفر + صفحه‌بندی تاریخچه
   (`scope=completed&page=n`).
4. **تب انبار/سیلو** — خواندن از `products.current_stock` (اندپوینت KPI همین را می‌دهد) به‌جای
   `/api/warehouses` که روی **هر دو** محیط صفر رکورد دارد.
5. **نام محصول در بارهای راننده** — جوین `products.name` به‌جای «نامشخص».
